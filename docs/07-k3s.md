# Single-node K3s operations

[Project overview](../README.md) · [Roadmap](06-roadmap.md)

## Design and pinned distribution

Installed on 2026-10-25 inside existing VM 200, without Proxmox host changes or VM recreation. K3s `v1.36.5+k3s1` was the official stable-channel version observed at installation. Kubernetes is v1.36.5; containerd is `2.3.4-k3s1.36`. SQLite is the embedded single-server datastore; there is no external database or embedded etcd cluster. This is a production-inspired learning environment with a single failure domain, not a highly available production service.

Defaults retained: containerd, CoreDNS, Flannel VXLAN, network-policy controller, Traefik, ServiceLB, local-path storage, and the packaged metrics-server. No Rancher, Prometheus, Grafana, Argo CD, or GitOps controller was installed. Secret encryption at rest is enabled; encryption configuration and server tokens remain only on the guest.

Non-secret effective configuration and reproducible assets are in [`kubernetes/k3s`](../kubernetes/k3s/): `config.yaml`, `install.sh`, `api-guard.nft`, its systemd unit and K3s dependency, and `smoke.yaml`. The installer refuses an existing installation; use a separately reviewed upgrade workflow rather than rerunning it on this cluster.

Official references: [requirements](https://docs.k3s.io/installation/requirements), [configuration](https://docs.k3s.io/installation/configuration), [server options](https://docs.k3s.io/cli/server), [SQLite selection](https://docs.k3s.io/datastore), [stable channel](https://update.k3s.io/v1-release/channels/stable), and [pinned release](https://github.com/k3s-io/k3s/releases/tag/v1.36.5%2Bk3s1). The server minimum is 2 CPU cores and 2 GB RAM, excluding workload resources. Keep added workloads small and measure remaining capacity.

## Repeatable installation

First repeat the health, capacity, address, and zero-drift checks. Stop for insufficient resources or an unhealthy guest. Transfer this directory to the verified guest through strict-host-key SSH, then run inside the guest:

```sh
cd /path/to/kubernetes/k3s
sudo ./install.sh
```

The script installs the non-secret YAML configuration and persistent guest firewall before invoking the official installer with `INSTALL_K3S_VERSION=v1.36.5+k3s1`. It verifies the installer SHA-256; the official installer verifies the release binary checksum. Recorded installer digest: `e5cc3b3d9dfc1662c2d9be6da5abc9a4cd317d6abc3a5ffc02e3dd3248207fee`. Installed amd64 binary digest: `d73847bcd3c5fccef0115b372e2f9a91f3032dc84bbf71518a4617565294d313`. If the mutable installer changes, inspect it and deliberately update the recorded checksum before use. These checksums are integrity evidence, not an independently verified release signature.

The initial installation used the same official pinned distribution and reached Node Ready. Validation identified a listener configuration issue: loopback-only binding prevents pods reaching the advertised API endpoint; explicitly switching bind-address to 0.0.0.0 then caused a TLS self-check against that wildcard address. The effective configuration omits both bind-address and advertise-address, allowing K3s default listener and DHCP node-address selection. CoreDNS was restarted to clear startup retry backoff. Traefik's installer retried while CRDs became available, then completed successfully. The repository captures the corrected settings, with the firewall installed before startup.

## Access and network boundaries

Use `kubectl` as ubuntu on the guest. `/home/ubuntu/.kube` has mode 0700. Its `config` is a symlink to the canonical `/etc/rancher/k3s/k3s.yaml`, owned root:ubuntu with mode 0640. K3s maintains that group and mode on restart. This avoids stale copied certificates. This is administrative access; do not share it with application users or commit the kubeconfig.

The API listens using the K3s default listener so pods can reach the advertised endpoint. The guest-only `k3s_api_guard` nftables table drops packets arriving on eth0 to TCP 6443, 6444, 10250 and UDP 8472, for both IP families. The systemd guard is enabled and required before k3s starts. It does not flush or replace K3s network rules. No Proxmox/router firewall changes or public forwarding were made. Direct LAN access to 6443 was blocked and incremented the guard's drop counter. Use guest-local kubectl through SSH; do not open the API publicly.

Pod CIDR is 10.42.0.0/16; service CIDR is 10.43.0.0/16; cluster DNS is 10.43.0.10. IPv4 forwarding is enabled by K3s and the node has its 10.42.0.0/24 CNI route. Flannel uses eth0. There are no additional nodes, so inbound VXLAN on eth0 is unnecessary and blocked. Adding nodes requires a reviewed network and capacity design.

Traefik and ServiceLB expose HTTP/HTTPS on the private guest IP, ports 80/443, and allocate NodePorts. The guest firewall added here protects control-plane ports, not every workload port. UFW remains inactive. Router exposure is not audited; do not add public forwarding. The test ingress uses `smoke.lab.invalid` and plain HTTP; trusted ingress TLS and application access policy remain future work. DHCP remains in use; check the current lease and MAC before connecting. A reservation/internal DNS remains planned.

## Validation and smoke test

Run on the guest after installation or maintenance:

```sh
systemctl is-active k3s k3s-api-guard
systemctl is-enabled k3s k3s-api-guard
kubectl get --raw=/readyz
kubectl wait --for=condition=Ready node/lab-k3s-01 --timeout=90s
kubectl -n kube-system wait --for=condition=Available deployment --all --timeout=90s
kubectl get pods -A -o wide
kubectl top node
sudo k3s secrets-encrypt status
sudo nft list table inet k3s_api_guard
```

The smoke manifest creates an isolated `platform-smoke` namespace, ConfigMap, one small non-root HTTP deployment, ClusterIP service, Traefik ingress, and a finite DNS/service job. Resource requests and limits are explicit; containers drop capabilities and use a read-only root filesystem.

```sh
kubectl apply -f smoke.yaml
kubectl -n platform-smoke rollout status deployment/smoke-web --timeout=180s
kubectl -n platform-smoke wait --for=condition=complete job/smoke-network --timeout=180s
kubectl -n platform-smoke logs job/smoke-network
curl -fsS -H 'Host: smoke.lab.invalid' http://192.168.10.226/
```

Expected HTTP body: `enterprise-platform-lab-ok`. The job tests internal Kubernetes DNS, external github.com DNS, and pod-to-service HTTP. For a rerun, delete only the completed `smoke-network` job and reapply the manifest. The LAN resolver returned NXDOMAIN for example.com from both the guest and pods; github.com and archive.ubuntu.com resolved successfully. The smoke check uses github.com to avoid conflating that upstream result with a cluster failure.

## Operational limits and recovery

Keep kubeconfig, server tokens, encryption configuration, SQLite files, and backups outside Git. The admin kubeconfig grants full cluster access. Encrypt backups and restrict access. [SQLite backup guidance](https://docs.k3s.io/datastore/backup-restore) requires the database directory and server token; plan a consistent backup and test restoration before relying on this cluster for important data. Local-path volumes and SQLite share the VM disk and do not provide redundancy. No restore exercise or off-VM K3s backup was completed in this milestone.

Do not run the uninstall or killall scripts as a routine recovery action. First check service health, resource pressure, events, DNS, and the guest firewall dependency. For an approved version upgrade, take a protected backup, review release notes and compatibility, pin the chosen version, and repeat validation. No automatic upgrade controller is installed.

A guest reboot was used to validate enabled services and workload recovery; this is distinct from changing Proxmox configuration. Recheck DHCP identity before reconnecting after maintenance. Leave guest patching, trusted ingress TLS, scoped application RBAC, backups, and GitOps as explicit follow-up milestones.
